# Design: HTTP gateway to the bus

## Context

Prototype gateway: 35 lines of Deno over the Deno bus SDK, no auth, `gw` effectively root (see
proposal). After `component-bus` and `bus-acl-biscuit`: instances are processes started by tilrd
with an inherited fd; every call is authorized by a Biscuit — the connection's own or the call's
`credential` (bearer); tokens are minted by the owner (`tilr bus token`), bound to the server,
expiring, revocable. tilrd already serves HTTP on its port for `/metrics` and `/socks` with an
Origin allowlist (`access-control`).

## Goals / Non-goals

Goals: HTTP callers (scripts, local tools, a browser page the owner allows) call bus methods with
exactly the rights of the token they present; no ambient authority; safe defaults on a local
port. Non-goals: see proposal.

## Decisions

### D1. Rust, inside the tilrd executable
The gateway is security-facing code (parsing HTTP from any local process); in this Rust workspace
it gets the same clippy, deny, nextest and MSRV gates as tilrd, and ships in the one archive per
platform without changing the CDN layout (`tilrd` + `tilr`) or adding a runtime dependency (Deno)
on users' machines. It is a separate process (an instance), not a part of the supervisor, so a
crash or overload of the gateway does not touch panes. Rejected: keeping the Deno gateway (Deno
on every machine; JS outside the repo's CI); a third binary (changes the archive layout and every
reader of it); serving `/call` from tilrd's own port (puts HTTP request parsing for the bus in
the supervisor and mixes two authentication schemes on one port).

### D2. Built-in modules
`[modules.gateway] builtin = "gateway"` (instead of `command`) runs the current tilrd executable
as `tilrd gateway [ARGS…]`, with `args` from the module or instance. After tilrd reloads into a
new executable, instances of built-in modules are reloaded one at a time so they run the same
version as the supervisor.

```toml
[modules.gateway]
builtin = "gateway"
[instances.http]
module = "gateway"
args = ["--listen", "127.0.0.1:8787"]
```

### D3. Bind and request hygiene
`--listen ADDR:PORT` (default `127.0.0.1:8787`); an address that is not loopback is refused at
start (`the gateway listens on loopback only`), so the instance fails to start and the bus reports
`start_failed`. `Host` must be `localhost`, `127.0.0.1` or `[::1]` with or without the port, else
421 (DNS rebinding). A request with an `Origin` header is refused 403 unless the origin is listed
with `--allow-origin` (exact match, as tilrd's own check); preflight `OPTIONS` answered only for
listed origins. HTTP/1.1 only.

### D4. Authentication and rights
`Authorization: Bearer <base64url Biscuit>` is required; missing or not base64url = 401 with
`WWW-Authenticate: Bearer` and no bus call. The bytes go as `Call.credential`; the broker decides
(`bus-acl-biscuit` D4, D7). The gateway instance has no rights of its own (an empty `rights`
table is the expected config; a non-empty one is logged as a warning). It never caches
decisions; it does not verify tokens itself (it has no root key).

### D5. Mapping
- `POST /call/<method>` → `Call{method, target: ""}`; `POST /call/<instance>/<method>` →
  `target: <instance>`. Names validated as in `component-bus` (400 if not).
- Request `Content-Type` → `Call.content_type`; reply `content_type` → response `Content-Type`
  (default `application/octet-stream`); body bytes unchanged both ways.
- `X-Tilr-Timeout-Ms` → `Call.timeout_ms` (positive integer, else 400).
- Trace id generated by the gateway (`gw-<random>`) and returned in `X-Tilr-Trace`.
- Errors: JSON `{"error":{"code","message"}}` with `denied` 403, `not_found` 404, `unavailable`
  503, `busy` 429 (`Retry-After: 1`), `timeout` 504, `too_large` 413, `bad_request` 400,
  `not_supported` 501, anything else 500.

### D6. Limits
Body ≤ `max_frame` minus 64 KiB of envelope (413 before reading the rest), headers ≤ 16 KiB
(431), 256 requests in flight (503 `busy` above, without calling the bus), idle keep-alive 60 s,
request read timeout 30 s. Each limit bounds memory.

### D7. Logs
One access line per request: method, path, status, duration, trace id; no `Authorization`
header, no bodies. Authorization outcomes are in the broker's audit (`bus-acl-biscuit` D9).

## Reload and reconnect

The gateway holds no state. tilrd's reload keeps the instance (handover); after a reload into a
new executable it is reloaded (D2). An HTTP request in flight during a gateway reload gets its
connection closed; one in flight during tilrd's exec gets 503 (`unavailable`).

## Backpressure

D6 bounds the gateway; the bus's own limits (`component-bus` D4) apply behind it: a `busy` from
the broker becomes 429.

## Risks / Trade-offs

- `hyper` is a new dependency tree (`cargo deny`).
- Loopback only: any local process with a token can call; that is the point of the token.
- A browser page needs an allowed origin and a token in script, so a token in a page is as
  exposed as the page; documented.

## Open Questions

- D1 Rust inside the tilrd executable vs a separate binary vs Deno. Rec.: inside tilrd (archive
  layout and CI unchanged, no Deno at run time).
- D3 non-loopback binds refused. Rec.: refuse until TLS is designed (Docker and NATS also default
  to local or require TLS for remote clients).
- D4 Bearer header only, no query-string token. Rec.: header only (query strings end in logs and
  browser history; tilrd's own `?token=` exists for WebSocket clients that cannot set headers).
