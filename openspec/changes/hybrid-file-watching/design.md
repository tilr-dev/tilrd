# macOS hybrid watcher research

Research date: 2026-10-27. Proposed parameters below are starting budgets, not measured performance or accepted product defaults. No architecture choice is made by this document.

## Current behavior and constraints

Daemon: `crates/tilrd/src/files.rs:715–799` takes a names snapshot, creates a notify RecommendedWatcher per request, registers NonRecursive, discards errors/rescan metadata, and batches paths for 100 ms. Direct-child existence and the names cache determine CREATE/MODIFY/REMOVE. Temporary save files are hidden. Replacement, unwatch and disconnect own cleanup. The snapshot precedes native registration. `openspec/specs/files/spec.md` requires nonrecursive changes, coalescing, exactly one MODIFY for protocol saves, and permits change delivery before the save acknowledgement.

App: `Sources/Tilr/FolderWatcher.swift:11–31` in desktop-mac uses recursive FileEvents, SinceNow, the main queue, and deliberately omits NoDefer to avoid double reloads. It ignores flags and IDs; stream start is unchecked. `Sources/Tilr/Config.swift:442` and site-serving specify 0.2 s batching by default. `Tab.swift:225` chooses plugin HMR or page reload from paths; `main.swift:78` separately watches config.yml by suffix. Unloaded tabs have no watcher. A few site roots do not imply a few descendant directories.

Existing owner decisions favor real native files, event-driven updates with periodic reconciliation, and an embedded sync core. The October 7 push target is approximately 10 ms end to end on a LAN; File Provider was superseded for that latency goal. The directory-sync design is separate and unchanged. Current FsWatch/app batching already exceeds that target, so changing FSEvents alone cannot meet it.

## Native semantics and the observed delay

Directory EVFILT_VNODE watches attach to the directory inode. NOTE_WRITE is the useful hint for entry-list changes; NOTE_EXTEND is not a portable promise for every directory operation. Also subscribe to DELETE, RENAME, REVOKE and ATTRIB to manage lifecycle. Notifications are coalesced hints without child names. Listing/diffing identifies entries. An in-place write to an existing child does not require modifying its parent's listing, and a root descriptor does not recursively observe descendants. A directory vnode hybrid therefore accelerates atomic-save rename/create/delete in covered directories, not arbitrary content writes. [Apple kevent semantics](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kevent.2.html), [vnode registration](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/KernelQueues/KernelQueues.html).

Handle MustScanSubDirs as subtree invalidation. UserDropped or KernelDropped invalidates all watched coverage of the affected stream; scan the full watched coverage, not just one event path. Register before the baseline scan and retain changes during scanning. RootChanged requires path revalidation. Event ID wrap, mount transitions and restart also invalidate trust. These are advisory events, so periodic reconciliation is still required. [Apple FSEvents guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html).

The local trace places the delay after kernel delivery, in fseventsd processing. One worker woke every 15 s for about 10 ms; observed path-processing delay was 20–75 s, both with and without the probe. This excludes the Rust wrapper and the configured native latency as sufficient explanations. It does **not** establish why the daemon adopted that rhythm: scheduling, internal timers/policy and host state remain unproven. No public Apple contract examined promises delivery within the requested latency, or documents a universal 15 s mode. Reducing latency or repeatedly flushing is not a proven fix.

This class of failure is not unique to this machine: Watchman documents out-of-order delayed observations even after FlushSync on busy hosts, and upstream users report service synchronization timeouts. Those reports establish external risk, not prevalence or the same local root cause. [Watchman's observed synchronization limitation](https://facebook.github.io/watchman/docs/cookies), [upstream timeout report](https://github.com/facebook/watchman/issues/1157). No host configuration change is proposed on this evidence.

## Options and honest latency envelope

Let W be unique daemon directories, D app descendant directories, N indexed entries, K a fixed directory-watch cap, H entries in the hot scan set, P its period, and R the cold sweep period. Descriptor counts below exclude opaque framework internals and existing networking; no FSEvents option pins every watched file open.

| Option | Persistent explicit FDs | CPU / metadata work | Discovery delay before existing batching | Complexity / coverage |
| --- | --- | --- | --- | --- |
| FSEvents only, small latency | No per-file/dir vnode FDs | O(events), O(N) on loss | Usually quick; unbounded service stall | Low; current failure remains |
| Directory vnode for every directory + FSEvents | W+1 daemon; D+1 app | O(changed-directory listing), O(events) | Entry changes bypass service; in-place content still waits | Medium; violates daemon scaling constraint |
| **Bounded directory vnode set + FSEvents + metadata sweeps** | At most K+1 per process, plus bounded scan handles | O(events + H/P + N/R) metadata/sec | Covered entry changes: scheduling + listing; others: native event or scan visit | Medium/high; recommended candidate, no global 10 ms bound |
| Metadata polling all entries every 10 ms | Bounded transient handles | About 100N metadata checks/sec | Up to period + sweep time, no OS deadline | Simple concept, high CPU/cache/disk cost, rejected candidate |
| Per-file kqueue | O(N) | Event driven | Direct content hints | Owner rejected |
| Endpoint Security investigation | Different privileged/entitled deployment | Broad machine event filtering | Requires feasibility/latency study | Not a drop-in library; separate architectural route if universal fast external edits are mandatory |

## Candidate A: bounded hybrid, recommended for owner evaluation

### Daemon FsWatch

1. Share registrations for identical canonical directories and retain per-client watch names/ownership. Keep the native FSEvents source for all active watches. Bound application queues: paths become dirty sets; queue overflow collapses to a root invalidation rather than dropping silently. Do not recursively change FsWatch semantics.
2. One kqueue and at most **64 directory FDs per daemon process** as an initial budget, selected from active client watches by recent demand. Do not watch all configured roots or all files. Eviction closes the old FD; coverage continues through FSEvents and sweeps. EMFILE/access/revoke failures use the same fallback, never cause an admission loop. Promote on subscriptions or observed activity, not on every timer tick. K is a proposed policy, not a new public setting in this research.
3. Directory hints enqueue a direct-entry metadata reconciliation. A successful FsWrite can enqueue its committed destination directly, independent of fseventsd. Feed it through the same coalescer and generation-aware deduplication; delayed native reports must not create a second notification for the same committed version, or suppress a later edit. No event before commit; failed writes and temporary paths remain invisible. This is an implementation candidate requiring deterministic regression coverage, not a replacement for external-write observation.
4. Suggested hot metadata visits: **1 s**; fair cold full-coverage objective: **60 s**. One global scheduler, including event-triggered reconciliation, uses at most 2 ms CPU work per 200 ms (1% of one core as a scheduling target), capped at 1,000 metadata entries/s, one I/O scan worker and small resumable chunks. No timer per file. Under load, periods stretch and scan age is reported; neither 1 s nor 60 s is a guarantee. Service stall without callbacks is caught by periodic scans, not by a quiet-stream timeout falsely diagnosing an idle tree.

### Tilr.app recursive sites

1. FSEvents continues to cover each loaded tree. A shared vnode pool watches site roots first, then eligible descendant directories up to **256 directory FDs per app process**, including all tabs and the config directory. A few roots alone cannot cover nested atomic saves. Identical roots share coverage; unload/close releases subscriptions. Discovery of new directories installs a watch before scanning where budget permits; excess directories receive periodic scan coverage.
2. Suggested hot visits: **250 ms** for the current site's recently used assets; cold tree objective: **30 s**, with the same global work budget as above. Site selection supplies demand even if FSEvents is stalled. Hash-based phase offsets stagger roots reproducibly. Polling does not wake unloaded sites or recursively read content.
3. Reconciliation yields concrete changed paths for the existing dot-path filters and plugin HMR decision. An uncertainty that cannot be reduced to paths invalidates/reloads the full loaded site. Config root invalidation must explicitly re-read config.yml; passing a bare directory path to the existing suffix filter would miss it. Keep scan I/O off the main queue, serialize lifecycle and deliver callbacks on main.
4. Preserve watch.latency, including its 0.2 s default, with one app-level batching stage for all sources. NoDefer can be assessed only with that stage and burst tests; blindly adding it duplicates reloads. Lowering app batching or daemon's 100 ms contract needs an explicit owner choice and the corresponding spec scope.

### Reconciliation correctness and lifecycle

- Snapshot entry name, type, file identity, size, nanosecond mtime and ctime, and relevant mode/link information. A directory's mtime/size is only an entry-list hint; never skip child stats solely because it is unchanged. Same-size overwrites with restored mtime can still differ in ctime, but metadata is not a cryptographic content identity. Same-metadata rewrites and create-delete entirely between visits are outside scan detection; do not claim a full event log. Mandatory byte-exact anti-entropy needs separately budgeted hashes/content verification.
- Apply events as invalidations, then reconcile the current state. A delayed path event without a changed version is a no-op. Retain positive invalidation for same-metadata native content hints; time-based suppression alone can hide real edits. Root loss is REMOVE for daemon watchers; recreated-path policy follows explicit re-registration rather than silently tracking a different inode. The app can revalidate a configured path under its existing site lifecycle.
- Register native sources before baseline enumeration. Tag scan chunks with a generation and preserve a per-root dirty generation until a pass covering it completes. Changes during a pass schedule another bounded pass without losing dirty state. Coalesce repeated loss hints to one recovery job; sustained churn exposes degraded coverage and never creates parallel recrawl storms. An incomplete/denied listing retains prior entries as unknown rather than emitting mass REMOVE. Recheck authorization and confinement, do not follow a newly introduced symlink outside allowed roots, and do not hydrate provider files to compare bytes.
- Fair scheduling reserves some service for old dirty/cold roots so hot traffic cannot starve them. Maintain root count, last completed sweep age, degraded roots, entries checked, scan CPU/wall time, FD coverage and event-to-report latency in implementation diagnostics; exact public metrics/log contract is left to implementation proposals. Budget includes baseline/loss/event-triggered scans, not just timers. A single blocked filesystem call cannot be preempted by a CPU budget; remote/cloud filesystems have no latency bound.
- Watch state stays ephemeral: after supervisor exec/restart, rebuild registrations and baseline; clients reconnect/re-watch. Cancel generation tokens on unwatch/disconnect and discard in-flight completions; dedup state never survives a different registration. Preserve the existing bulk-lane delivery/backpressure contract; bound pending notification paths and reconcile again after saturation, rather than allocate an unbounded raw-event queue. Future persistent sync indices belong to the separate sync engine.

## Work and latency estimates, not benchmarks

At N=10,000 entries, a 60 s sweep averages 167 checks/s; 30 s averages 333/s. At N=1,000,000, 60 s needs 16,667 checks/s and exceeds the proposed 1,000/s cap: a cold sweep takes at least 1,000 s even before hot work. A hot set H=100 every 250 ms adds 400/s; every 1 s adds 100/s. Naive 10 ms polling of 10,000 entries needs 1,000,000 checks/s.

If a warm metadata check costs c microseconds, CPU demand is checks/s × c / 10,000 percent of one core, plus enumeration, allocation and dispatch. At an **illustrative, unmeasured** c=10 µs, 167/s is 0.167%, 1,000/s is 1%, and 1,000,000/s is 1,000%. Cold disk, cache misses and provider metadata can cost much more wall time. Filesystem enumeration reads metadata pages, not necessarily file bytes; no universal bytes/s estimate follows from N. Cached snapshots cost O(N) memory; entry and dirty-set caps must trigger an explicit degraded/error outcome rather than silently abandon coverage. Descriptor cap is a hard admission limit; CPU percentage is a cooperative scheduling target to measure.

For a covered atomic save, discovery may plausibly take milliseconds on a warm local filesystem, but there is no new measurement proving 10 ms here. Notification then includes the daemon's 100 ms or app's configured batching. External in-place writes use the first of FSEvents and their next metadata visit; cold uncapped paths can take sweep age. Neither kqueue-on-parent nor cheap metadata polling can guarantee arbitrary external modifications throughout a huge tree within 10 ms under the stated constraints.

## Owner choice and follow-up slices

**A (recommended candidate):** adopt bounded hybrid recovery with best-effort fast covered entry changes and honest scan-age diagnostics. Decide explicitly whether the approximately 10 ms target applies only to a future fast sync path/known writes, or must also cover arbitrary external in-place writes. This candidate does not satisfy that universal target by itself.

**B:** retain universal approximately 10 ms external-write discovery as a prerequisite, and commission a separate feasibility study (entitled Endpoint Security, bounded explicit hot files if permitted, or another OS integration). A general Endpoint Security client requires an Apple-granted entitlement, root privileges and Full Disk Access approval; this changes deployment and needs explicit evaluation. [Apple client requirements](https://developer.apple.com/documentation/endpointsecurity/client), [entitlement](https://developer.apple.com/documentation/BundleResources/Entitlements/com.apple.developer.endpoint-security.client). No claim that this route is feasible, deployable or sufficient yet. The existing owner prohibition on holding all files open remains in force.

After selection, split implementation into daemon registration/recovery/reporting and app recursive coverage/HMR/config lifecycle. Each must land its integration tests with the behavior. Daemon tests: fake-clock stalled source plus real protocol FsWrite, duplicate native callback after a scan, create/remove/root loss, admission cap, invalidation during baseline, unwatch/reconnect, permission failures and cancellation. App tests: recursive atomic save, in-place nested overwrite, config invalidation, plugin HMR versus full reload, overflow and unload cleanup. Native tests must synchronize on registration and observed callbacks, without sleeps/retries or enlarged deadlines. A separate performance experiment on local APFS records OS/build, storage/cache state, N/W/D, syscall count, CPU, physical metadata I/O and p50/p95/p99 discovery and notification delay for warm/cold scans, 10k and 1m-entry workloads. No implementation latency acceptance criterion is silently weakened by this research.
